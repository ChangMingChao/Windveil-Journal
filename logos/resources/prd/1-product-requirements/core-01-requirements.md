# 未发生事件管理局 需求文档

> 最后更新：2026-09-05
> 模块：core（核心功能）｜阶段：Phase 1 产品需求（Why）

## 一、产品背景与目标

### 1.1 产品定位

未发生事件管理局是一个**个人愿望陪伴产品**：收集那些你不想错过的未来，并在你准备好时，陪它们慢慢发生。

它不是待办工具。用户在这里记录的是**不适合立刻执行、却不希望被遗忘的愿望**——想一个人去看海、想在冬天学会滑雪、想重新开始画画、想在父母还健康时多陪他们旅行、想在三十岁前完成一次长途徒步。系统不以完成率压迫用户，而是长期保存、理解等待，并在时机合适时温柔地让一件事开始发生。

一句话定位：**为那些还没发生、但值得被认真对待的事，留一盏灯。**

产品人格：Agent 不是效率教练（「你已逾期 12 天，请立即完成」），而是了解你的记录者与同行者（「你在春天说过想重新画画。最近你的日程比之前松了一些，要不要从十分钟的速写开始？」）。

设计原则（贯穿全部场景的验收基准）：

1. 不制造焦虑，不强调连续打卡。
2. 不滥用提醒，只有值得出现时才出现。
3. 不替用户定义「应该做什么」。
4. 接受愿望被修改、暂停，甚至被放下。
5. 将「完成」理解为经历，而不是勾选。

### 1.2 核心目标

| 目标 | 衡量指标 | 第一版目标值 |
|------|---------|-------------|
| 记录门槛足够低 | 新用户首次打开 → 种下第一个愿望的耗时 | ≤ 90 秒 |
| 愿望被真正写下来 | 新用户首日种下 ≥ 1 个愿望的比例 | ≥ 60% |
| 长期陪伴而非短期效率 | 第 30 天回访率 | ≥ 35% |
| 时机判断有效 | 时机到达后 7 天内产生任意用户动作（推进／顺延／放下）的愿望占比 | ≥ 50% |
| 不制造焦虑 | 每位用户平均每周收到的主动提醒条数 | ≤ 3 条 |
| 不制造焦虑 | 因提醒过多而关闭通知或注销的用户比例 | ≤ 5% |
| 确实让事情发生 | 使用满 90 天的用户中至少 1 件愿望进入「已经发生」的比例 | ≥ 30% |

**明确的非目标指标**：完成率、连续打卡天数、任务数排行、日活强化。产品内不采集、不展示、不用于任何激励文案。

### 1.3 目标用户画像

**主画像 — 林澪，29 岁，一线城市互联网从业者**

工作强度高，脑子里长期存着七八件「等不忙了就去做」的事：一个人去海边待两天、把画笔重新拿起来、带父母去一次南方。曾经用过待办类工具，但每次打开都看到一片逾期红字，最后连应用一起删掉。他们不缺执行力，缺的是一个不催促、能替他们把这些事认真保存住的地方。

- 使用设备：手机为主（通勤、睡前），偶尔桌面浏览器。
- 使用频率：想到一件事时随手记录（每周 0–3 次），主动回看每月 1–2 次。
- 最在意的：不被评判、内容私密、写下来不会变成新的负债。

**次画像 — 沈原，41 岁**

有明确的人生清单意识（父母的年纪、孩子的成长阶段），愿望的时间窗口是真实存在且不可逆的。更看重「已发生之书」的沉淀价值，愿意补充照片和文字。

## 二、用户痛点分析

### P01: 愿望没有合适的容器，只能留在脑子里

因为 现有工具要求填写截止日期、明确步骤和优先级，而「想一个人去看海」此刻既没有日期也没有步骤 → 导致 用户不愿意把这类事写进任何工具，只能靠记忆保管 → 造成 愿望被日常事务覆盖并遗忘，多年后只剩下「本来想去的」这种模糊遗憾。

### P02: 效率工具把愿望变成新的负债

因为 待办工具用逾期、完成率、连续打卡来衡量用户 → 导致 写下一件本来令人期待的事，反而变成一条持续提醒你失败的记录 → 造成 用户为了减轻压力而删除条目、关闭通知，最终整体弃用工具。

### P03: 记下来了，却永远等不到「开始」

因为 愿望的启动依赖时机（季节、心情、空闲、预算、同行的人），而工具只会按固定日期提醒 → 导致 提醒总在错误的时候出现并被顺手划掉 → 造成 记录变成死档，写下与不写下没有区别。

### P04: 想开始时不知道第一步是什么

因为 一件愿望在脑中是一个巨大的整体（「去看海」= 请假 + 订票 + 行程 + 预算 + 天气），工具不会帮它拆开 → 导致 每次想起都因为「太重了」而搁置 → 造成 明明有意愿，仍然迟迟无法启动。

### P05: 完成之后什么都没有留下

因为 工具的终点是把事项勾掉并归档 → 导致 真正发生过的经历没有被记录，只剩一个已完成标记 → 造成 用户无法回看自己活过的部分，也失去了继续种下新愿望的动力。

### P06: 放下一个愿望会带来羞耻感

因为 工具把「未完成」等同于失败，没有为「不再想做了」提供体面的出口 → 导致 用户既不敢动手做、也不敢删除，任其堆积成过期列表 → 造成 打开应用等于面对一堆自我指责，索性不再打开。

## 四、核心场景详述

### S01: 新用户建立自己的未发生之地

- **触发条件**：新用户首次打开产品（未注册或未完成初始化）
- **用户价值**：在不被要求填表的前提下，拥有一个只属于自己的、可以安心存放未来的地方，并带着第一张愿望卡离开首次体验（← P01, P02）
- **优先级**：P0
- **主路径**：
  1. 用户看到一句欢迎语和一组「关于未来的温柔问题」（2–4 题，例如「最近有什么事，你一直想做但还没做？」）
  2. 用户逐题回答，也可以点击顶部的「先直接写一个愿望」跳过全部问题
  3. 用户以文字或语音写下第一件想在未来发生的事
  4. Agent 将其转为一张愿望卡，并轻问一句（用户可以不回答）
  5. 用户进入「未发生之地」，看到自己的第一张卡片；账号与个人隐私空间已建立

#### 验收条件

##### 正常：完整走完温柔问题并种下第一个愿望
- **GIVEN** 一位新用户首次打开产品，尚未建立个人空间
- **WHEN** 用户依次回答全部温柔问题，在最后一步输入「等压力没这么大的时候，想去海边待两天」并提交
- **THEN** 系统建立仅该用户可见的个人空间，生成一张状态为「刚种下」的愿望卡（标题为 Agent 提炼的短句、保留用户原话、标注种下月份），Agent 追问一句（如「这更像是一次独处，还是想和某个人一起去？」），页面随后进入「未发生之地」并展示该卡片

##### 正常：跳过温柔问题直接种下
- **GIVEN** 一位新用户处于温柔问题的第 1 题
- **WHEN** 用户点击「先直接写一个愿望」
- **THEN** 系统跳过全部剩余问题直接进入输入界面，用户提交后仍生成愿望卡并进入「未发生之地」；已回答的问题（若有）不丢失，未回答的问题不再追问、不产生任何补全提示或红点

##### 异常：跳过问题后又不输入任何内容就退出
- **GIVEN** 用户已跳过温柔问题，停留在输入界面且输入框为空
- **WHEN** 用户点击返回或直接关闭页面
- **THEN** 系统仍完成个人空间的建立，「未发生之地」显示空状态文案（不含任何「你还没有完成设置」类提示或进度条），入口保持为一个输入框；下次打开不再重复温柔问题流程

##### 异常：Agent 理解服务不可用
- **GIVEN** 用户已输入一句愿望，此时 Agent 理解服务超时或返回失败
- **WHEN** 用户点击提交
- **THEN** 系统仍完整保存用户原话并生成愿望卡（标题回退为用户原话的前 20 字，状态为「刚种下」），页面提示「先替你收好了，我稍后再慢慢读它」，不出现技术错误码，不要求用户重试或重新输入

### S02: 随手种下一个愿望并被理解

- **触发条件**：已有用户临时想到一件想在未来发生的事，打开首页输入入口
- **用户价值**：一句话、不填表就能把一个模糊的念头交出去，并确认它被理解成了自己真正想要的东西（← P01, P04）
- **优先级**：P0
- **主路径**：
  1. 用户在首页唯一的输入入口（「今天，有什么想在未来发生的事吗？」）用文字或语音说出一句话，可附一张照片
  2. Agent 从模糊表达中提取：真正想要的感受（放松／陪伴／勇气／连接／成长）、隐含条件（时间、地点、预算、季节、同行的人）、一个最小可行动步骤
  3. Agent 轻问一句以补齐最关键的缺口，用户可以回答，也可以跳过
  4. 生成愿望卡（标题、种下时间、用户原话、状态「刚种下」），并进入「未发生之地」

#### 验收条件

##### 正常：一句话文字输入生成愿望卡
- **GIVEN** 已建立个人空间的用户处于首页输入入口
- **WHEN** 用户输入「想在冬天学会滑雪」并提交
- **THEN** 系统在 5 秒内生成愿望卡，卡面包含标题「学会滑雪」、「种下于 2026 年 9 月」、用户原话、状态「刚种下」；Agent 结构化结果中记录感受倾向与隐含条件「季节：冬季」，并给出一个最小下一步；Agent 追问不超过 1 句

##### 正常：语音输入并跳过追问
- **GIVEN** 用户处于首页输入入口并已授予麦克风权限
- **WHEN** 用户按住录音说出一段不超过 60 秒的话并松手提交，随后对 Agent 的追问点击「先不说」
- **THEN** 系统转写语音、保留原始音频、生成愿望卡；追问被记录为「待未来再问」但当次不再追问，且不因此阻塞卡片生成

##### 异常：输入内容不构成一件未来想做的事
- **GIVEN** 用户处于首页输入入口
- **WHEN** 用户提交「今天下午 3 点开会」这类当下的日程事项
- **THEN** 系统仍保存该条内容，并以询问而非纠正的方式确认（如「这更像是这几天要办的事，还是你想在未来发生的事？」），提供「就当成一件未来的事」与「删掉它」两个选择，不自动丢弃用户输入

##### 异常：语音转写失败或权限被拒绝
- **GIVEN** 用户尝试使用语音输入，但浏览器麦克风权限被拒绝或转写返回失败
- **WHEN** 用户提交录音
- **THEN** 权限被拒时提示一次授权引导并保留已输入的文字内容；转写失败时保留原始音频并生成标题为「一段还没被读懂的话」的愿望卡，可在详情页重试转写或改为手动输入，不丢失录音

### S03: 为一个愿望约定属于它的时机

- **触发条件**：用户希望某件事在合适的时候被想起，而不是被定期催促
- **用户价值**：把「什么时候该想起这件事」的定义权交回自己手里，从此可以放心地不去想它（← P03, P02）
- **优先级**：P0
- **主路径**：
  1. 用户打开愿望详情页，选择「什么时候再提起它」
  2. 用户从自主触发条件中选择一项：某个季节到来／某个月份或纪念日／N 个月后／当我有一个空闲周末时／当我主动提到很累时／不必提醒，我自己会想起
  3. 系统将卡片状态从「刚种下」转为「正在酝酿」，卡面显示这个约定（如「正在等待合适的风：入冬」）
  4. 时机到达时，用户收到一条温柔的通知（Web Push 或邮件），措辞不含催促
  5. 用户可以选择「我好像准备好了」（进入 S04）或「还不是现在」（顺延，重新约定）

#### 验收条件

##### 正常：约定季节触发并在时机到达时收到通知
- **GIVEN** 用户有一张状态为「刚种下」的愿望卡「学会滑雪」，当前为 2026 年 9 月
- **WHEN** 用户在详情页选择触发条件「某个季节到来 → 冬季」并保存
- **THEN** 卡片状态转为「正在酝酿」，卡面展示「正在等待合适的风：入冬」；到达约定时机后系统发送 1 条通知，文案引用用户原话（如「你在九月说过想在冬天学会滑雪，冬天到了」），并提供「我好像准备好了」与「还不是现在」两个动作；同一时机不重复发送第二条通知

##### 正常：时机到达但用户选择顺延
- **GIVEN** 某张卡片的约定时机已到达，用户已收到通知
- **WHEN** 用户点击「还不是现在」
- **THEN** 卡片保持「正在酝酿」，系统请用户重新约定一个时机（默认建议顺延 3 个月），卡面不出现逾期标记、不累计未响应次数、不降低该愿望在「未发生之地」中的展示位置

##### 异常：用户选择不设置任何提醒
- **GIVEN** 用户在触发条件选择界面
- **WHEN** 用户选择「不必提醒，我自己会想起」
- **THEN** 卡片状态保持「刚种下」，系统不再对该愿望发送任何主动通知，卡面标注「你说你会自己想起它」，且详情页仍可随时补设时机

##### 异常：同一时间窗口内多张卡片同时触发
- **GIVEN** 用户有 5 张卡片的约定时机落在同一周
- **WHEN** 这些时机相继到达
- **THEN** 系统在该周内最多发送 3 条主动通知（超出部分按用户设置时间的先后顺延到下一周），其余卡片在应用内以柔和标记呈现而不发送推送；系统不会将多条愿望合并成一条清单式的催办通知

> 来源：holiday-aware-timing 提案（路线图第 2 步「工具调用与外部数据源」的节假日部分）。以下验收条件追加到 S03 的验收条件之后；天气与个人日历数据源不在本提案范围。

#### 验收条件（节假日感知增补）

##### 正常：free_weekend 命中真实的休息日
- **GIVEN** 用户所在年份的节假日数据已内置，且当前临近一个含调休的假期（如国庆：10/1–10/8 休假、10/10 周六调休上班）
- **WHEN** 用户为某愿望设置时机「当我有一个空闲周末时」
- **THEN** 服务端计算的触发日不落在调休上班的周六/周日上，命中下一个真实休息日；触发时刻沿用既有的上午约定；卡面与提醒文案不受影响

##### 正常：时机建议的理由可以引用节假日
- **GIVEN** 用户生成时机建议，且提议时点临近法定长假
- **WHEN** Agent 产出建议
- **THEN** 建议的有界上下文包含节假日事实，理由可以引用它（如「因为 10/1–10/8 是国庆长假，之后第一个周末更从容」）；该建议的依据列表包含 `calendar` 类条目；确认后的提醒链路行为与手动约定完全一致

##### 异常：调休上班的周末不被当作「空闲周末」
- **GIVEN** 某周六为法定调休上班日
- **WHEN** 服务端为 free_weekend 计算触发日
- **THEN** 该周六被跳过；若同周日也是调休上班日则一并跳过，直到命中第一个非调休的周末日

##### 异常：节假日数据缺失时安全退化
- **GIVEN** 服务端没有某个年份的节假日数据文件（如次年数据尚未随版本发布）
- **WHEN** 该年份内请求 free_weekend 计算或生成时机建议
- **THEN** 计算退化为「不考虑节假日」的现状语义（下一个周六/周日），不报错、不阻塞记录与建议；建议依据列表中不出现 `calendar` 条目

### S04: 风来了，开始第一小步

- **触发条件**：约定时机到达后用户愿意推进，或用户在任意时刻主动点击「我好像准备好了」
- **用户价值**：不需要面对整件事，只需要完成一个两分钟就能做完的动作，就算已经开始（← P04, P03）
- **优先级**：P0
- **主路径**：
  1. 用户在通知或卡片上点击「我好像准备好了」，卡片状态转为「风来了」
  2. 用户与 Agent 在详情页对话，Agent 给出**一个**很小的下一步（如「今晚花两分钟，收藏一张你想看的海的照片」），而不是一整套计划
  3. 用户完成这一小步并标记，或告诉 Agent 自己想换一个更小的开始
  4. 卡片状态转为「正在发生」，准备过程被逐条记录在详情页
  5. 用户愿意时，Agent 才逐步协助确定日期、整理预算、规划行程、建立提醒

#### 验收条件

##### 正常：完成第一小步并进入「正在发生」
- **GIVEN** 某张卡片状态为「正在酝酿」，用户已点击「我好像准备好了」
- **WHEN** Agent 给出一个最小下一步，用户完成后点击「做完了」
- **THEN** 卡片状态转为「正在发生」，该步骤连同完成时间被记入详情页的准备过程；Agent 单次仅追加下一个小步骤，不一次性列出剩余全部计划；系统不为该愿望设置任何截止日期

##### 正常：用户要求一个更小的开始
- **GIVEN** Agent 已给出一个最小下一步，用户认为仍然太重
- **WHEN** 用户点击「还是太难了，换一个更小的」
- **THEN** Agent 在同一轮内给出一个更轻的替代步骤（限定为可在 5 分钟内独立完成、不涉及花钱与联系他人），且不重复此前被拒绝的步骤

##### 异常：进入「正在发生」后长期没有新动作
- **GIVEN** 某张卡片状态为「正在发生」，且连续 60 天没有任何用户动作
- **WHEN** 系统进行状态回看
- **THEN** 系统最多发送 1 条以询问为主的关心（如「那件事最近怎么样了？还想继续吗？」），提供「继续推进」「先放回酝酿」「安静放下」三个选择；不显示停滞天数、不显示进度百分比、不发送第二条追问

##### 异常：用户在推进过程中改变了愿望本身
- **GIVEN** 某张卡片状态为「正在发生」，原愿望为「一个人去海边待两天」
- **WHEN** 用户在对话中表示「想改成和妹妹一起去」
- **THEN** 系统更新愿望内容与隐含条件，同时完整保留原话与首次种下时间（详情页显示「最初你说的是……」），已记录的准备过程不被清空，状态保持「正在发生」

### S05: 回看未发生之地并重新整理

- **触发条件**：用户打开主界面回看自己的愿望，或某个愿望的心境已经改变
- **用户价值**：像走进自己的花园一样回看那些还没发生的事，并且可以体面地修改、暂停或放下其中任何一件（← P06, P02）
- **优先级**：P1
- **主路径**：
  1. 用户打开「未发生之地」，以愿望花园／时间河流的形式浏览全部卡片（而非列表）
  2. 用户按状态浏览：刚种下／正在酝酿／风来了／正在发生／已经发生／安静放下
  3. 用户打开某张卡片，修改内容、暂停提醒，或选择「安静放下」
  4. 被放下的卡片移入「安静放下」区域，保留原话与种下时间，不被删除、不被标记为失败
  5. 花园重新回到可呼吸的状态，不出现任何逾期或未完成计数

#### 验收条件

##### 正常：按状态浏览愿望花园
- **GIVEN** 用户拥有 12 张分布在 4 种不同状态的愿望卡
- **WHEN** 用户打开「未发生之地」并切换到「正在酝酿」
- **THEN** 页面以卡片形式（含标题、种下时间、用户原话摘要、状态文案）展示对应卡片；界面中不出现「完成率」「逾期」「连续天数」「待办数量」任何一项；卡片默认按种下时间排序，用户可切换为按时机临近排序

##### 正常：安静放下一个愿望
- **GIVEN** 某张卡片状态为「正在酝酿」
- **WHEN** 用户在详情页选择「安静放下」并确认
- **THEN** 卡片状态转为「安静放下」并移入对应区域，保留标题、原话与首次种下时间；系统停止该愿望的全部主动通知；确认文案与结果文案均不含「失败」「放弃」「未完成」字样（如「它曾被认真保存过，随时可以再回来」）

##### 异常：用户尝试彻底删除一个愿望
- **GIVEN** 用户希望不再看到某个愿望
- **WHEN** 用户选择「彻底删除」
- **THEN** 系统先说明「安静放下」与「彻底删除」的区别（放下可随时唤回，删除不可恢复），二次确认后才执行删除；删除为不可恢复操作，且连同该愿望的语音、照片与对话记录一并清除

##### 异常：花园为空
- **GIVEN** 用户已放下或删除全部愿望，「未发生之地」当前没有任何进行中的卡片
- **WHEN** 用户打开主界面
- **THEN** 页面展示与首次进入一致的温暖空状态与单一输入入口，不出现引导补齐、成就中断或「你已经很久没有记录了」类提示

### S06: 把发生过的事写成一页记忆

- **触发条件**：用户标记某个愿望「已经发生」
- **用户价值**：一件事结束后不是被勾掉，而是变成一页可以反复回看的记忆，长期积累成个人的「已发生人生档案」（← P05）
- **优先级**：P0
- **主路径**：
  1. 用户在详情页标记「已经发生」，并填写发生的日期或时间区间
  2. Agent 依据愿望原话与准备过程草拟一页记忆（起因、经过、当时的期待）
  3. 用户补充照片、声音、心情与一句话，可自由修改 Agent 写的任何一段
  4. 记忆页存入「已发生之书」，卡片状态转为「已经发生」
  5. 用户可按时间浏览已发生之书，回看任意一页

#### 验收条件

##### 正常：生成并补充一页记忆
- **GIVEN** 某张卡片状态为「正在发生」，愿望为「一个人去海边待两天」，详情页已有 3 条准备过程记录
- **WHEN** 用户标记「已经发生」，填写日期 2026 年 10 月 17 日—18 日，补充 2 张照片、心情与一句话「原来我不是不想努力，只是需要喘口气」
- **THEN** 系统生成记忆页，包含标题、发生日期区间、引用的原始期待（「你原本想逃离一点压力」）、用户补充的照片／心情／原话；该页存入「已发生之书」并可按时间浏览；愿望卡状态转为「已经发生」且不再接收任何提醒

##### 正常：跳过全部补充内容
- **GIVEN** 用户已标记某愿望「已经发生」
- **WHEN** 用户不补充任何照片、声音或文字，直接保存
- **THEN** 系统仅以愿望原话、准备过程与发生日期生成记忆页并正常入册；页面不出现「内容不完整」提示或完成度指示，且支持日后随时补充

##### 异常：未经历约定路径就直接标记已发生
- **GIVEN** 某张卡片状态为「刚种下」，没有任何准备过程记录
- **WHEN** 用户直接标记「已经发生」
- **THEN** 系统允许该操作（承认事情可能在产品之外自然发生），仅追问发生日期与一句话感受，并据此生成记忆页；不强制要求补齐中间状态

##### 异常：发生日期早于种下日期
- **GIVEN** 某愿望的种下时间为 2026 年 9 月
- **WHEN** 用户填写发生日期为 2026 年 7 月
- **THEN** 系统以询问方式确认（如「它比你写下它的时候更早发生了吗？」），用户确认后照原样保存并在记忆页注明，不做硬性拦截、不弹出校验错误

### S07: 唤回一个被安静放下的愿望

- **触发条件**：用户在很久之后重新想起一件曾经放下的事，并主动进入「安静放下」区打开它
- **用户价值**：曾经放下的事不必从零开始，它的原话与最初的心动都还在（← P06, P01）
- **优先级**：P2；本次提升进第一版 launched 后的首个增量范围
- **主路径**：用户在「安静放下」区域打开卡片 → 查看当初的原话、首次种下时间与放下时间 → 选择「重新种下」→ 保留首次种下时间，状态回到「刚种下」→ 用户可继续复用 S03 重新约定时机
- **范围裁剪**：本次只覆盖用户主动从「安静放下」区唤回；「在种下新愿望时命中已放下的相似记录」需要 Agent 相似度判断与 S02 分支，另行提案处理

##### 正常：从安静放下区重新种下
- **GIVEN** 某愿望状态为「安静放下」，且保留了标题、原话、首次种下时间与放下时间
- **WHEN** 用户在 `/garden?state=安静放下` 打开该卡片并点击「重新种下」
- **THEN** 系统将该愿望状态改回「刚种下」；`seeded_at`、标题、原话、照片与准备过程时间线均保留；`let_go_at` 清空；不会自动生成提醒、不会立即调用 Agent，也不会出现「重新开始失败」类错误文案

##### 正常：唤回后重新约定时机
- **GIVEN** 用户已经把一个愿望从「安静放下」重新种下，状态为「刚种下」
- **WHEN** 用户点击「约定一个时机」并按 S03 选择季节、月份、几个月后、空闲周末、疲惫信号或不必提醒
- **THEN** 系统完全复用 S03 的时机规则进入「正在酝酿」或保持无提醒状态；首次种下时间仍按原始时间展示，不显示「重新种下次数」或任何负担式计数

##### 异常：从非安静放下状态尝试重新种下
- **GIVEN** 某愿望状态不是「安静放下」
- **WHEN** 客户端或重复请求调用「重新种下」
- **THEN** 服务端拒绝本次状态迁移并保持原状态不变；用户界面静默刷新最新卡片，不用羞辱性文案解释「你操作错了」

##### 异常：访问他人的安静放下愿望
- **GIVEN** 用户 A 拿到了用户 B 的愿望 id
- **WHEN** 用户 A 请求详情或调用「重新种下」
- **THEN** 服务端统一返回 404 而非 403；不暴露该愿望是否存在；安全审计日志只记录 user_id 与被请求 id，不记录愿望内容

### S08: 管理偏好与可用时段

- **触发条件**：用户想知道系统记住了自己什么并加以修正；或在约定时机时被问到「什么时候有空」，想一次性把自己的空闲规律说清楚
- **用户价值**：对自己的记忆保有完全的查看、修正与清除权；同时让「空闲周末」这类时机有真实的依据，而不是被随机追问（← P03, P01）
- **优先级**：P1
- **主路径**：
  1. 用户从「未发生之地」右上角进入「我的」，打开「它记得我什么」
  2. 页面分两区列出偏好与可用时段：每条偏好标注来源（「你说过的」/「我猜的」+ 置信度），可用时段按周展示
  3. 用户可以声明一条偏好（覆盖同主题的猜测）、撤回一条不准确的推断、彻底删除任何一条，也可以添加、修改或删除可用时段（如「周六上午通常有空」）
  4. 之后在 S03 的「当我有一个空闲周末时」时机与 Agent 的时机建议中，系统按可用时段判断，而不是靠反复追问

#### 验收条件

##### 正常：查看记忆并声明一条偏好
- **GIVEN** 用户打开「它记得我什么」，看到一条来源为「我猜的」的偏好「喜欢一个人做事（置信度 60%）」
- **WHEN** 用户声明「其实更想和朋友一起」，保存后回看该主题
- **THEN** 新增一条来源为「你说过的」的偏好，原「我猜的」条目保持原样且明确并列展示（不互相覆盖、不丢失）；此后涉及该主题的时机建议以「你说过的」优先；两条均可在页面上分别删除

##### 正常：撤回一条模型推断
- **GIVEN** 用户看到一条来源为「我猜的」的偏好
- **WHEN** 用户点击「猜错了」撤回它
- **THEN** 该条立即从默认列表消失，并保留一条「你已撤回」的审计痕迹（含撤回时间）供用户回看；系统不再把它用于任何时机判断； Agent 后续不再基于同一依据重复该推断

##### 异常：模型提议未经确认不会变成任何提醒
- **GIVEN** Agent 依据偏好、可用时段与历史记录给出了一条时机建议（含建议日期、理由与置信度）
- **WHEN** 用户尚未点击确认
- **THEN** 该建议只停留在应用内的「待确认」状态，不进入提醒队列、不发送任何推送或邮件、不改变愿望状态；用户拒绝或忽略后，系统按原时机继续，不自行改写用户已约定的时机

##### 异常：删除是彻底的，不留任何影子
- **GIVEN** 用户删除一条偏好（无论来源）或一个可用时段
- **WHEN** 删除完成
- **THEN** 该条从数据库中硬删除且不可恢复；不出现在任何导出、任何后续的模型摘要或上下文中；若它曾被纳入某条已生成的时机建议，该建议一并标记失效，不会继续引用已删除的内容

### S09: 先记一下并随手划掉

- **触发条件**：用户冒出一个当下的小事（今晚吃什么、周末取快递、回个电话），不值得开一张愿望卡、更不值得被提醒
- **用户价值**：一句话把它放下来，随手划掉就完了；它不会进入任何提醒队列，不占用每周提醒额度（← P01, P02）
- **优先级**：P1
- **主路径**：
  1. 用户在 P1 种下页选择「先记一下」（次级入口，与「种下愿望」的主输入并存）
  2. 输入一句话（如「今晚吃火锅」）并保存，轻事件出现在下方的轻事件列表里
  3. 做完之后随手「划掉」，或不想留了「收走」
  4. 轻事件全程与愿望互不影响：不进提醒队列、不被 Scheduler 扫描、不占每周 3 条提醒额度

#### 验收条件

##### 正常：记下并划掉
- **GIVEN** 用户处于 P1 种下页
- **WHEN** 用户点「先记一下」，输入「今晚吃火锅」并保存，随后点「划掉了」
- **THEN** 轻事件立即出现在列表中；划掉后从默认列表消失，状态记录为已完成（`done`，含时间）；全程不产生任何提醒记录、不改变任何愿望

##### 正常：轻事件在结构上不产生提醒
- **GIVEN** 某用户本周提醒额度已用满（3 条），且持有若干轻事件
- **WHEN** 该用户记录、查看或划掉轻事件
- **THEN** 提醒发件箱不出现任何轻事件相关记录；既有的愿望提醒顺延行为完全不受影响；「轻事件无提醒」由数据与代码结构保证（轻事件表无触发时间字段、不在调度器扫描集合中），而非仅靠约定

##### 异常：空内容不保存
- **GIVEN** 用户在「先记一下」输入框
- **WHEN** 输入为空或仅空白字符时尝试保存
- **THEN** 前端保存按钮禁用；服务端对空内容返回 422；不产生空记录

##### 异常：收走是彻底的，不留影子
- **GIVEN** 用户对一条轻事件点「收走」（彻底清除）
- **WHEN** 删除完成
- **THEN** 该条从数据库硬删除且不可恢复；重复收走返回 404；不出现在任何导出或统计中；界面无「已清除 N 条」类计数

- **触发条件**：用户想安静一段时间、只想收邮件不想收推送、或想把推送重新打开
- **用户价值**：安静是用户的选择而不是需要确认的操作——一键全关、随时恢复，已确认的时机一件不丢（← P02）
- **优先级**：P1
- **主路径**：
  1. 用户进入 P6「我的」的「提醒通道」区，看到推送与邮件两个开关的当前状态
  2. 切换任一开关，立即生效（无冷静期、无确认弹层）
  3. 关闭推送后，之后的提醒只走邮件；两个都关则完全静默，已到期的提醒顺延等待
  4. 重新打开后，顺延中的提醒自然恢复投递

#### 验收条件

##### 正常：关闭推送、保留邮件
- **GIVEN** 用户已注册推送订阅，且有一个时机即将到期的愿望
- **WHEN** 用户关闭「推送」开关（邮件保持开启）
- **THEN** 下一次投递直接走邮件（不先尝试已关闭的推送通道）；已注册的订阅数据保留；重新打开推送后投递恢复双通道

##### 正常：全部关闭 = 完全静默，已确认的时机不丢失
- **GIVEN** 用户的 outbox 中已有 pending 的提醒记录（来自其已确认的时机）
- **WHEN** 用户关闭全部通道
- **THEN** 调度器不再投递任何内容（应用内也不出现催促标记）；pending 记录不被删除、按顺延规则等待；重新打开任一通道后，顺延中的提醒自然恢复投递且受周预算约束

##### 异常：开关切换立即生效且互不牵连
- **GIVEN** 用户在连续操作中快速切换两个开关
- **WHEN** 每次切换保存
- **THEN** 每次保存只改变目标开关，另一开关状态保持不变；愿望、轻事件、偏好等数据不受任何影响；响应即时返回最新状态

## 五、约束与边界

- **产品形态**：第一版为**移动优先的 Web 应用（可安装为 PWA）**，不做原生 App、不做桌面客户端。
- **语音输入**：依赖浏览器录音能力与服务端语音转写，需保留原始音频以便转写失败后重试（见 S02 异常条件）。
- **提醒通道**：Web Push 为主、邮件为兜底。iOS Safari 仅在用户将 PWA 添加到主屏后才能接收 Web Push，因此**邮件通道为必选项**，不可作为可选功能裁剪。**通道由用户自控（S10 增补）**：推送与邮件各有独立开关、切换立即生效；推送关闭时投递直接走邮件；全部关闭时完全静默，已确认时机的提醒顺延等待、重开后恢复。
- **Agent 能力**：愿望理解、追问、最小下一步生成依赖大语言模型，必须具备不可用降级路径——保存用户原文并延后理解，不得因模型失败而阻塞记录（见 S01／S02 异常条件）。
- **Agent 时机建议边界（S08 增补）**：大模型在时机问题上只产出**结构化建议**（建议的时机类型、参数、理由、置信度与依据），遵循「模型提议 → 服务端规则校验 → 用户确认 → 调度器执行」的链路；模型不得直接决定提醒何时发出，不得绕过校验或确认写入任何触发时间。
- **偏好记忆红线（S08 增补）**：偏好与可用时段数据区分「用户主动声明」与「模型推断」并标注来源与置信度；模型推断的内容可查看、可撤回、可彻底删除；定期生成的偏好摘要同属用户内容，同样可查看、可删除；这些数据应用层加密存储，且不将全部历史无界塞入模型上下文。
- **节假日数据源边界（holiday-aware-timing 增补）**：法定节假日与调休上班日采用**内置数据文件**（随镜像发布、年份粒度、无网络请求、无用户数据参与），数据缺失时计算安全退化为不考虑节假日；触发日计算与节假日判定一律在服务端完成，模型只在建议理由中引用服务端提供的节假日事实。
- **轻事件边界（S09 增补）**：轻量事件是**记录**不是愿望——独立存储、应用层加密、owner 隔离；**在结构上没有提醒路径**（无触发时间字段、不在调度器扫描集合、不进入提醒发件箱），因此天然不占用每周提醒额度；轻事件不调用 Agent，不做任何统计与计数。
- **隐私**：全部内容仅用户本人可见；愿望原话、语音与照片需加密存储；不做任何形式的跨用户内容推荐或聚合分析。
- **文案约束**：产品内禁止出现「任务」「截止」「逾期」「未完成」「打卡」「连续 N 天」等词汇，统一使用「种下」「酝酿」「风来了」「正在发生」「发生过」「安静放下」。

### 5.2 资源与时间约束

- 团队规模按 1–3 人的小团队规划，MVP 目标周期 8 周（**待用户确认**，见 5.4）。
- 第一版不引入自建模型训练、不引入实时协作基础设施。
- 视觉方向以「夜晚的信箱 + 植物生长」为隐喻（奶油白、雾蓝、暖棕、低饱和绿），细节在 Phase 2 产品设计阶段确定。

### 5.3 「不做」清单

| 不做的事 | 原因 |
|---------|------|
| 社交、多人协作、共同愿望 | 第一版聚焦个人隐私空间，社交会改变记录时的坦诚程度 |
| 愿望的私密性分级与对外分享卡 | 全部内容默认仅自己可见即已满足 MVP；分级会引入对外可见性并稀释「私密」这一前提 |
| 自动订票、支付、下单 | 涉及资金与外部账号，超出「陪伴」的边界 |
| 天气、位置与个人日历的自动推理 | 外部数据源按路线图分步落地：**法定节假日已以内置数据文件落地（holiday-aware-timing）**；天气需要供应商选型与数据出境评估、个人日历需要 OAuth 授权与隐私边界设计，各自独立提案 |
| 模型直接发送或改写提醒 | 模型只到「提议待确认」为止；提醒是否发出、何时发出仍由确定性调度器按用户已确认的时机决定 |
| ~~轻量日常事件（「晚上吃什么」类）~~ | **已落地为 S09（lightweight-events 提案）**：独立轻量记录表 + 「先记一下」入口，结构上无提醒路径；Agent 理解与轻事件建议仍不做（见下两条的同类理由） |
| 轻事件的 Agent 理解与建议 | 轻事件保持纯记录的零摩擦；任何理解与建议都会让「先记一下」变重，属后续增强 |
| 视频记录 | 现有媒体管道仅覆盖文字、语音与照片；视频需补 MIME 白名单、大小／时长上限、分片续传与存储成本控制，另行提案 |
| 强制打卡、连续天数、完成率、排行榜 | 与「不制造焦虑」原则直接冲突 |
| 通用聊天机器人入口 | Agent 只围绕愿望对话，避免产品定位漂移 |
| 原生 App、桌面客户端、多语言 | 形态与范围收敛，见 5.1 |

### 5.4 待确认事项

1. 团队规模与 MVP 目标周期（当前按 1–3 人 / 8 周假设推进）。
2. 语音转写服务选型与成本上限（影响 S02 的转写时延指标）。
3. 邮件发送服务选型（影响 S03 的提醒送达率）。
4. S07「唤回被安静放下的愿望」已确认提升为 launched 后首个增量：本次只做用户主动唤回，种下新愿望时的相似记录命中另行提案。
5. S08 偏好摘要的生成频率与保留期限（当前假设：每日低频生成、仅保留最近一份；影响存储与 LLM 成本，随 S08 实现一并确认）。
6. S08 时机建议的有效期（当前假设：7 天未确认自动失效；影响「待确认」堆积体验）。
7. 节假日数据的年度更新流程（holiday-aware-timing 落地后新增：每年官方公告发布后更新内置数据文件并随版本发布；发布前后的过渡期按「缺年份退化」语义运行）。
