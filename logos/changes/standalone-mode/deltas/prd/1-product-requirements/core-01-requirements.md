## MODIFIED — 五、约束与边界

## 五、约束与边界

- **产品形态**：第一版为移动优先的 Web 应用（可安装为 PWA）。**Android 端已收敛为纯单机应用（standalone-mode）**：数据存本机（Room）、不设登录账号，后端不再被 Android 消费；提醒走系统日历，邮件通道在 Android 端删除。backend/ 与 Web PWA 保持现状（服务端模式仍可用，本提案不维护双模切换）。
- **Android 模型分析（standalone-mode 增补）**：愿望理解、一句追问、最小步骤生成、时机建议全部复用心语的用户自配模型（客户端直连、配置仅存本地），分析过程在用户使用期间静默完成；模型未配置或调用失败一律降级——保存原话、跳过理解/建议，不阻塞记录（沿用既有 degraded 语义）。分析只发送最小必要上下文（原话与摘要）到用户自己配置的模型端点。
- **Android 提醒（standalone-mode 增补）**：约定时机时将「待发生事件」写入系统日历（CalendarProvider，需用户授权），由系统能力在触发时间提醒；触发时刻由端上确定性计算（移植后端 timing.py 算法，节假日数据文件随 APK 打包）。邮件通道在 Android 端删除；未授权日历或写入失败时降级为仅应用内展示。
- **数据可携带（standalone-mode 增补）**：设置页提供全量 JSON 导出（愿望/随手记/已发生之书），作为单机数据无服务端兜底的最低备份手段。
- **语音输入**：依赖浏览器录音能力与服务端语音转写，需保留原始音频以便转写失败后重试（见 S02 异常条件）。Android 端语音种下仍待后续迭代，当前以文本输入为主。
- **提醒通道**：Web 端维持 Web Push 为主、邮件为兜底；通道由用户自控（S10）。Android 端按 standalone-mode 修订：提醒只走系统日历，邮件通道删除。
- **Agent 能力**：愿望理解、追问、最小下一步生成依赖大语言模型，必须具备不可用降级路径——保存用户原文并延后理解，不得因模型失败而阻塞记录（见 S01／S02 异常条件）。Android 单机端以心语的用户自配模型承担该能力，降级语义一致。
- **Agent 时机建议边界（S08 增补）**：大模型在时机问题上只产出结构化建议（建议的时机类型、参数、理由、置信度与依据），遵循「模型提议 → 规则校验 → 用户确认 → 执行」的链路；模型不得直接决定提醒何时发出，不得绕过校验或确认写入任何触发时间。Android 单机端链路相同，校验与触发时刻计算由端上 TimingCalculator 承担。
- **偏好记忆红线（S08 增补）**：偏好与可用时段数据区分「用户主动声明」与「模型推断」并标注来源与置信度；模型推断的内容可查看、可撤回、可彻底删除；定期生成的偏好摘要同属用户内容，同样可查看、可删除；这些数据应用层加密存储，且不将全部历史无界塞入模型上下文。
- **节假日数据源边界（holiday-aware-timing 增补）**：法定节假日与调休上班日采用内置数据文件（随镜像发布、年份粒度、无网络请求、无用户数据参与），数据缺失时计算安全退化为不考虑节假日；触发日计算与节假日判定一律在服务端完成，模型只在建议理由中引用服务端提供的节假日事实。（Android 单机端同规则：数据文件随 APK 打包，计算由端上 TimingCalculator 完成。）
- **天气数据源边界（weather-data-source 增补）**：天气仅用于时机建议的理由与上下文，位置只来自用户在 P6 主动声明的「所在城市」偏好（走偏好加密/撤回/删除体系）——不使用 IP 推断、不使用浏览器定位、不做任何静默采集；未声明城市、供应商不可用或超时 5 秒时能力整体静默；天气是瞬时预报，不写入 evidence、不持久化、不建提醒。
- **轻事件边界（S09 增补）**：轻量事件是记录不是愿望——独立存储、应用层加密、owner 隔离；在结构上没有提醒路径（无触发时间字段、不在调度器扫描集合、不进入提醒发件箱），因此天然不占用每周提醒额度；轻事件不调用 Agent，不做任何统计与计数。（Android 单机端：本地 Room 表，无提醒路径同规则；心语识别的有用信息写入该表。）
- **隐私**：全部内容仅用户本人可见；愿望原话、语音与照片需加密存储；不做任何形式的跨用户内容推荐或聚合分析。（Android 单机端：数据全部在本机，仅分析上下文发往用户自配的模型端点。）
- **文案约束**：产品内禁止出现「任务」「截止」「逾期」「未完成」「打卡」「连续 N 天」等词汇，统一使用「种下」「酝酿」「风来了」「正在发生」「发生过」「安静放下」。

### 5.2 资源与时间约束

- 团队规模按 1–3 人的小团队规划，MVP 目标周期 8 周（**待用户确认**，见 5.4）。
- 第一版不引入自建模型训练、不引入实时协作基础设施。
- 视觉方向以「夜晚的信箱 + 植物生长」为隐喻（奶油白、雾蓝、暖棕、低饱和绿），细节在 Phase 2 产品设计阶段确定。

### 5.3 「不做」清单

| 不做的事 | 原因 |
|---------|------|
| 社交、多人协作、共同愿望 | 第一版聚焦个人隐私空间，社交会改变记录时的坦诚程度 |
| 愿望的私密性分级与对外分享卡 | 全部内容默认仅自己可见即已满足 MVP；分级会引入对外可见性并稀释「私密」这一前提 |
| 自动订票、支付、下单 | 涉及资金与外部账号，超出「陪伴」的边界 |
| 天气、位置与个人日历的自动推理 | 外部数据源按路线图分步落地：法定节假日已以内置数据文件落地（holiday-aware-timing）；天气已落地（weather-data-source）；个人日历（OAuth）仍待独立提案（Android 单机端的系统日历写入属提醒通道，非 OAuth 读取） |
| 模型直接发送或改写提醒 | 模型只到「提议待确认」为止；提醒是否发出、何时发出仍由确定性调度/日历按用户已确认的时机决定 |
| ~~轻量日常事件（「晚上吃什么」类）~~ | 已落地为 S09（lightweight-events 提案）：独立轻量记录表 + 「先记一下」入口，结构上无提醒路径 |
| 轻事件的 Agent 理解与建议 | 轻事件保持纯记录的零摩擦；任何理解与建议都会让「先记一下」变重，属后续增强 |
| 视频记录 | 现有媒体管道仅覆盖文字、语音与照片；视频需补 MIME 白名单、大小／时长上限、分片续传与存储成本控制，另行提案 |
| 强制打卡、连续天数、完成率、排行榜 | 与「不制造焦虑」原则直接冲突 |
| ~~通用聊天机器人入口~~（部分放开） | Android 心语入口已按用户决策放开（heart-voice-holiday-timing）：客户端直连用户自配的大模型端点，聊天产物仅按用户意图写入轻事件等既有结构；后端 Agent 仍只围绕愿望对话 |
| ~~原生 App~~（部分落地） | Android 原生客户端已落地（android-native-app，three-tomato 生成）；standalone-mode 后 Android 端为纯单机应用，iOS/鸿蒙/小程序等其他原生端与多语言仍不做 |
| 多语言 | 界面文案以中文为唯一语言，与文档语言策略一致 |
| Android 端的账号体系与邮件提醒（standalone-mode） | 用户决策：数据存本机不设登录账号；提醒只走系统日历，邮件通道在 Android 端删除（Web 端不变） |

### 5.4 待确认事项

1. 团队规模与 MVP 目标周期（当前按 1–3 人 / 8 周假设推进）。
2. 语音转写服务选型与成本上限（影响 S02 的转写时延指标）。
3. 邮件发送服务选型（影响 S03 的提醒送达率）。
4. S07「唤回被安静放下的愿望」已确认提升为 launched 后首个增量：本次只做用户主动唤回，种下新愿望时的相似记录命中另行提案。
5. S08 偏好摘要的生成频率与保留期限（当前假设：每日低频生成、仅保留最近一份；影响存储与 LLM 成本，随 S08 实现一并确认）。
6. S08 时机建议的有效期（当前假设：7 天未确认自动失效；影响「待确认」堆积体验）。
7. 节假日数据的年度更新流程（holiday-aware-timing 落地后新增：每年官方公告发布后更新内置数据文件并随版本发布；发布前后的过渡期按「缺年份退化」语义运行）。
8. Android 单机端节假日数据随 APK 更新的年度节奏（standalone-mode 新增：与第 7 条同源，随版本发布）。
