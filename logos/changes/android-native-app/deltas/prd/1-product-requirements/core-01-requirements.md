## MODIFIED — 五、约束与边界

## 五、约束与边界

- **产品形态**：第一版为**移动优先的 Web 应用（可安装为 PWA）**，不做桌面客户端。**Android 原生客户端已按用户决策增补落地（android-native-app）**：以既有 PRD 与 API 契约为输入、由 three-tomato（android-generator）生成 Kotlin + Jetpack Compose 原生工程，输出至 `.three-tomato/output/android/`，与 PWA 平行、互不替代；后端与 API 契约不变，不新增任何服务端工作。iOS/鸿蒙/小程序等其他原生端仍不做。
- **语音输入**：依赖浏览器录音能力与服务端语音转写，需保留原始音频以便转写失败后重试（见 S02 异常条件）。Android 端的语音种下（`source=voice`）待后续迭代，当前以文本输入为主（媒体预签名直传 API 已具备）。
- **提醒通道**：Web Push 为主、邮件为兜底。iOS Safari 仅在用户将 PWA 添加到主屏后才能接收 Web Push，因此**邮件通道为必选项**，不可作为可选功能裁剪。**通道由用户自控（S10 增补）**：推送与邮件各有独立开关、切换立即生效；推送关闭时投递直接走邮件；全部关闭时完全静默，已确认时机的提醒顺延等待、重开后恢复。Android 端的通道开关读写同一组端点（`PATCH /me/notification-channels`），FCM 推送投递待后续提案。
- **Agent 能力**：愿望理解、追问、最小下一步生成依赖大语言模型，必须具备不可用降级路径——保存用户原文并延后理解，不得因模型失败而阻塞记录（见 S01／S02 异常条件）。Android 端同样遵循 degraded 语义（跳过轻问、纸色提示条）。
- **Agent 时机建议边界（S08 增补）**：大模型在时机问题上只产出**结构化建议**（建议的时机类型、参数、理由、置信度与依据），遵循「模型提议 → 服务端规则校验 → 用户确认 → 调度器执行」的链路；模型不得直接决定提醒何时发出，不得绕过校验或确认写入任何触发时间。
- **偏好记忆红线（S08 增补）**：偏好与可用时段数据区分「用户主动声明」与「模型推断」并标注来源与置信度；模型推断的内容可查看、可撤回、可彻底删除；定期生成的偏好摘要同属用户内容，同样可查看、可删除；这些数据应用层加密存储，且不将全部历史无界塞入模型上下文。
- **节假日数据源边界（holiday-aware-timing 增补）**：法定节假日与调休上班日采用**内置数据文件**（随镜像发布、年份粒度、无网络请求、无用户数据参与），数据缺失时计算安全退化为不考虑节假日；触发日计算与节假日判定一律在服务端完成，模型只在建议理由中引用服务端提供的节假日事实。
- **天气数据源边界（weather-data-source 增补）**：天气仅用于时机建议的理由与上下文，位置**只来自用户在 P6 主动声明的「所在城市」偏好**（走偏好加密/撤回/删除体系）——不使用 IP 推断、不使用浏览器定位、不做任何静默采集；未声明城市、供应商不可用或超时 5 秒时能力整体静默；天气是瞬时预报，不写入 evidence、不持久化、不建提醒。
- **轻事件边界（S09 增补）**：轻量事件是**记录**不是愿望——独立存储、应用层加密、owner 隔离；**在结构上没有提醒路径**（无触发时间字段、不在调度器扫描集合、不进入提醒发件箱），因此天然不占用每周提醒额度；轻事件不调用 Agent，不做任何统计与计数。
- **隐私**：全部内容仅用户本人可见；愿望原话、语音与照片需加密存储；不做任何形式的跨用户内容推荐或聚合分析。Android 端的匿名空间与 Web 端互不相通；跨设备找回依赖既有邮箱绑定 + 登录端点。
- **文案约束**：产品内禁止出现「任务」「截止」「逾期」「未完成」「打卡」「连续 N 天」等词汇，统一使用「种下」「酝酿」「风来了」「正在发生」「发生过」「安静放下」。

### 5.2 资源与时间约束

- 团队规模按 1–3 人的小团队规划，MVP 目标周期 8 周（**待用户确认**，见 5.4）。
- 第一版不引入自建模型训练、不引入实时协作基础设施。
- 视觉方向以「夜晚的信箱 + 植物生长」为隐喻（奶油白、雾蓝、暖棕、低饱和绿），细节在 Phase 2 产品设计阶段确定。

### 5.3 「不做」清单

| 不做的事 | 原因 |
|---------|------|
| 社交、多人协作、共同愿望 | 第一版聚焦个人隐私空间，社交会改变记录时的坦诚程度 |
| 愿望的私密性分级与对外分享卡 | 全部内容默认仅自己可见即已满足 MVP；分级会引入对外可见性并稀释「私密」这一前提 |
| 自动订票、支付、下单 | 涉及资金与外部账号，超出「陪伴」的边界 |
| 天气、位置与个人日历的自动推理 | 外部数据源按路线图分步落地：**法定节假日已以内置数据文件落地（holiday-aware-timing）**；天气需要供应商选型与数据出境评估、个人日历需要 OAuth 授权与隐私边界设计，各自独立提案 |
| 模型直接发送或改写提醒 | 模型只到「提议待确认」为止；提醒是否发出、何时发出仍由确定性调度器按用户已确认的时机决定 |
| ~~轻量日常事件（「晚上吃什么」类）~~ | **已落地为 S09（lightweight-events 提案）**：独立轻量记录表 + 「先记一下」入口，结构上无提醒路径；Agent 理解与轻事件建议仍不做（见下一条的同类理由） |
| 轻事件的 Agent 理解与建议 | 轻事件保持纯记录的零摩擦；任何理解与建议都会让「先记一下」变重，属后续增强 |
| 视频记录 | 现有媒体管道仅覆盖文字、语音与照片；视频需补 MIME 白名单、大小／时长上限、分片续传与存储成本控制，另行提案 |
| 强制打卡、连续天数、完成率、排行榜 | 与「不制造焦虑」原则直接冲突 |
| ~~通用聊天机器人入口~~（部分放开） | **Android 心语入口已按用户决策放开（android-native-app）**：客户端直连用户自配的大模型端点（url/api key 在应用「我的」页配置），聊天产物仅按用户意图写入轻事件等既有结构；后端 Agent 仍只围绕愿望对话，不做服务端通用聊天 |
| ~~原生 App~~（部分落地） | **Android 原生客户端已按用户决策落地（android-native-app，three-tomato 生成）**：消费既有 API、零服务端变更，与 PWA 平行；桌面客户端、iOS/鸿蒙/小程序等其他原生端与多语言仍不做，见 5.1 |
| 多语言 | 界面文案以中文为唯一语言，与文档语言策略一致 |

### 5.4 待确认事项

1. 团队规模与 MVP 目标周期（当前按 1–3 人 / 8 周假设推进）。
2. 语音转写服务选型与成本上限（影响 S02 的转写时延指标）。
3. 邮件发送服务选型（影响 S03 的提醒送达率）。
4. S07「唤回被安静放下的愿望」已确认提升为 launched 后首个增量：本次只做用户主动唤回，种下新愿望时的相似记录命中另行提案。
5. S08 偏好摘要的生成频率与保留期限（当前假设：每日低频生成、仅保留最近一份；影响存储与 LLM 成本，随 S08 实现一并确认）。
6. S08 时机建议的有效期（当前假设：7 天未确认自动失效；影响「待确认」堆积体验）。
7. 节假日数据的年度更新流程（holiday-aware-timing 落地后新增：每年官方公告发布后更新内置数据文件并随版本发布；发布前后的过渡期按「缺年份退化」语义运行）。
