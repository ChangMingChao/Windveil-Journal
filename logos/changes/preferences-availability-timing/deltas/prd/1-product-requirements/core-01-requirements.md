| 自检项 | 结论 |

## ADDED — S08: 管理偏好与可用时段

- **触发条件**：用户想知道系统记住了自己什么并加以修正；或在约定时机时被问到「什么时候有空」，想一次性把自己的空闲规律说清楚
- **用户价值**：对自己的记忆保有完全的查看、修正与清除权；同时让「空闲周末」这类时机有真实的依据，而不是被随机追问（← P03, P01）
- **优先级**：P1
- **主路径**：
  1. 用户从「未发生之地」右上角进入「我的」，打开「它记得我什么」
  2. 页面分两区列出偏好与可用时段：每条偏好标注来源（「你说过的」/「我猜的」+ 置信度），可用时段按周展示
  3. 用户可以声明一条偏好（覆盖同主题的猜测）、撤回一条不准确的推断、彻底删除任何一条，也可以添加、修改或删除可用时段（如「周六上午通常有空」）
  4. 之后在 S03 的「当我有一个空闲周末时」时机与 Agent 的时机建议中，系统按可用时段判断，而不是靠反复追问

#### 验收条件

##### 正常：查看记忆并声明一条偏好
- **GIVEN** 用户打开「它记得我什么」，看到一条来源为「我猜的」的偏好「喜欢一个人做事（置信度 60%）」
- **WHEN** 用户声明「其实更想和朋友一起」，保存后回看该主题
- **THEN** 新增一条来源为「你说过的」的偏好，原「我猜的」条目保持原样且明确并列展示（不互相覆盖、不丢失）；此后涉及该主题的时机建议以「你说过的」优先；两条均可在页面上分别删除

##### 正常：撤回一条模型推断
- **GIVEN** 用户看到一条来源为「我猜的」的偏好
- **WHEN** 用户点击「猜错了」撤回它
- **THEN** 该条立即从默认列表消失，并保留一条「你已撤回」的审计痕迹（含撤回时间）供用户回看；系统不再把它用于任何时机判断； Agent 后续不再基于同一依据重复该推断

##### 异常：模型提议未经确认不会变成任何提醒
- **GIVEN** Agent 依据偏好、可用时段与历史记录给出了一条时机建议（含建议日期、理由与置信度）
- **WHEN** 用户尚未点击确认
- **THEN** 该建议只停留在应用内的「待确认」状态，不进入提醒队列、不发送任何推送或邮件、不改变愿望状态；用户拒绝或忽略后，系统按原时机继续，不自行改写用户已约定的时机

##### 异常：删除是彻底的，不留任何影子
- **GIVEN** 用户删除一条偏好（无论来源）或一个可用时段
- **WHEN** 删除完成
- **THEN** 该条从数据库中硬删除且不可恢复；不出现在任何导出、任何后续的模型摘要或上下文中；若它曾被纳入某条已生成的时机建议，该建议一并标记失效，不会继续引用已删除的内容

## MODIFIED — 5.1 技术约束

### 5.1 技术约束

- **产品形态**：第一版为**移动优先的 Web 应用（可安装为 PWA）**，不做原生 App、不做桌面客户端。
- **语音输入**：依赖浏览器录音能力与服务端语音转写，需保留原始音频以便转写失败后重试（见 S02 异常条件）。
- **提醒通道**：Web Push 为主、邮件为兜底。iOS Safari 仅在用户将 PWA 添加到主屏后才能接收 Web Push，因此**邮件通道为必选项**，不可作为可选功能裁剪。
- **Agent 能力**：愿望理解、追问、最小下一步生成依赖大语言模型，必须具备不可用降级路径——保存用户原文并延后理解，不得因模型失败而阻塞记录（见 S01／S02 异常条件）。
- **Agent 时机建议边界（S08 增补）**：大模型在时机问题上只产出**结构化建议**（建议的时机类型、参数、理由、置信度与依据），遵循「模型提议 → 服务端规则校验 → 用户确认 → 调度器执行」的链路；模型不得直接决定提醒何时发出，不得绕过校验或确认写入任何触发时间。
- **偏好记忆红线（S08 增补）**：偏好与可用时段数据区分「用户主动声明」与「模型推断」并标注来源与置信度；模型推断的内容可查看、可撤回、可彻底删除；定期生成的偏好摘要同属用户内容，同样可查看、可删除；这些数据应用层加密存储，且不将全部历史无界塞入模型上下文。
- **隐私**：全部内容仅用户本人可见；愿望原话、语音与照片需加密存储；不做任何形式的跨用户内容推荐或聚合分析。
- **文案约束**：产品内禁止出现「任务」「截止」「逾期」「未完成」「打卡」「连续 N 天」等词汇，统一使用「种下」「酝酿」「风来了」「正在发生」「发生过」「安静放下」。

## MODIFIED — 5.3 「不做」清单

### 5.3 「不做」清单

| 不做的事 | 原因 |
|---------|------|
| 社交、多人协作、共同愿望 | 第一版聚焦个人隐私空间，社交会改变记录时的坦诚程度 |
| 愿望的私密性分级与对外分享卡 | 全部内容默认仅自己可见即已满足 MVP；分级会引入对外可见性并稀释「私密」这一前提 |
| 自动订票、支付、下单 | 涉及资金与外部账号，超出「陪伴」的边界 |
| 复杂的日历／天气／位置自动推理 | 外部数据源（节假日、天气、日历）的**工具化接入**按变更提案路线放在偏好与可用时段落地之后单独提案；本阶段时机建议只依据用户在产品内声明的偏好、可用时段与自己的记录，不抓取任何外部服务 |
| 模型直接发送或改写提醒 | 模型只到「提议待确认」为止；提醒是否发出、何时发出仍由确定性调度器按用户已确认的时机决定 |
| 轻量日常事件（「晚上吃什么」类） | 属于轻意图，把它装进愿望状态机会变成有提醒压力的愿望；后续以独立事件类型或轻量记录表另行提案，并配「先记一下」入口，不占用每周提醒额度 |
| 视频记录 | 现有媒体管道仅覆盖文字、语音与照片；视频需补 MIME 白名单、大小／时长上限、分片续传与存储成本控制，另行提案 |
| 强制打卡、连续天数、完成率、排行榜 | 与「不制造焦虑」原则直接冲突 |
| 通用聊天机器人入口 | Agent 只围绕愿望对话，避免产品定位漂移 |
| 原生 App、桌面客户端、多语言 | 形态与范围收敛，见 5.1 |

## MODIFIED — 5.4 待确认事项

### 5.4 待确认事项

1. 团队规模与 MVP 目标周期（当前按 1–3 人 / 8 周假设推进）。
2. 语音转写服务选型与成本上限（影响 S02 的转写时延指标）。
3. 邮件发送服务选型（影响 S03 的提醒送达率）。
4. S07「唤回被安静放下的愿望」已确认提升为 launched 后首个增量：本次只做用户主动唤回，种下新愿望时的相似记录命中另行提案。
5. S08 偏好摘要的生成频率与保留期限（当前假设：每日低频生成、仅保留最近一份；影响存储与 LLM 成本，随 S08 实现一并确认）。
6. S08 时机建议的有效期（当前假设：7 天未确认自动失效；影响「待确认」堆积体验）。
