### 场景粒度自检结论

| 自检项 | 结论 |
|--------|------|
| 单 API 测试 | 9 个场景均需多轮交互；S09 虽轻，仍含「记下 → 看到它 → 划掉/收走」的多步路径 |
| CRUD 测试 | S09 的读写不是 CRUD 拆分：验收对象是「轻意图有了零摩擦的去处且不产生任何提醒压力」，而非「数据被写入」；这正是把轻事件从愿望状态机里分出来的理由 |

## ADDED — S09: 先记一下并随手划掉

- **触发条件**：用户冒出一个当下的小事（今晚吃什么、周末取快递、回个电话），不值得开一张愿望卡、更不值得被提醒
- **用户价值**：一句话把它放下来，随手划掉就完了；它不会进入任何提醒队列，不占用每周提醒额度（← P01, P02）
- **优先级**：P1
- **主路径**：
  1. 用户在 P1 种下页选择「先记一下」（次级入口，与「种下愿望」的主输入并存）
  2. 输入一句话（如「今晚吃火锅」）并保存，轻事件出现在下方的轻事件列表里
  3. 做完之后随手「划掉」，或不想留了「收走」
  4. 轻事件全程与愿望互不影响：不进提醒队列、不被 Scheduler 扫描、不占每周 3 条提醒额度

#### 验收条件

##### 正常：记下并划掉
- **GIVEN** 用户处于 P1 种下页
- **WHEN** 用户点「先记一下」，输入「今晚吃火锅」并保存，随后点「划掉了」
- **THEN** 轻事件立即出现在列表中；划掉后从默认列表消失，状态记录为已完成（`done`，含时间）；全程不产生任何提醒记录、不改变任何愿望

##### 正常：轻事件在结构上不产生提醒
- **GIVEN** 某用户本周提醒额度已用满（3 条），且持有若干轻事件
- **WHEN** 该用户记录、查看或划掉轻事件
- **THEN** 提醒发件箱不出现任何轻事件相关记录；既有的愿望提醒顺延行为完全不受影响；「轻事件无提醒」由数据与代码结构保证（轻事件表无触发时间字段、不在调度器扫描集合中），而非仅靠约定

##### 异常：空内容不保存
- **GIVEN** 用户在「先记一下」输入框
- **WHEN** 输入为空或仅空白字符时尝试保存
- **THEN** 前端保存按钮禁用；服务端对空内容返回 422；不产生空记录

##### 异常：收走是彻底的，不留影子
- **GIVEN** 用户对一条轻事件点「收走」（彻底清除）
- **WHEN** 删除完成
- **THEN** 该条从数据库硬删除且不可恢复；重复收走返回 404；不出现在任何导出或统计中；界面无「已清除 N 条」类计数

## MODIFIED — 5.1 技术约束

### 5.1 技术约束

- **产品形态**：第一版为**移动优先的 Web 应用（可安装为 PWA）**，不做原生 App、不做桌面客户端。
- **语音输入**：依赖浏览器录音能力与服务端语音转写，需保留原始音频以便转写失败后重试（见 S02 异常条件）。
- **提醒通道**：Web Push 为主、邮件为兜底。iOS Safari 仅在用户将 PWA 添加到主屏后才能接收 Web Push，因此**邮件通道为必选项**，不可作为可选功能裁剪。
- **Agent 能力**：愿望理解、追问、最小下一步生成依赖大语言模型，必须具备不可用降级路径——保存用户原文并延后理解，不得因模型失败而阻塞记录（见 S01／S02 异常条件）。
- **Agent 时机建议边界（S08 增补）**：大模型在时机问题上只产出**结构化建议**（建议的时机类型、参数、理由、置信度与依据），遵循「模型提议 → 服务端规则校验 → 用户确认 → 调度器执行」的链路；模型不得直接决定提醒何时发出，不得绕过校验或确认写入任何触发时间。
- **偏好记忆红线（S08 增补）**：偏好与可用时段数据区分「用户主动声明」与「模型推断」并标注来源与置信度；模型推断的内容可查看、可撤回、可彻底删除；定期生成的偏好摘要同属用户内容，同样可查看、可删除；这些数据应用层加密存储，且不将全部历史无界塞入模型上下文。
- **节假日数据源边界（holiday-aware-timing 增补）**：法定节假日与调休上班日采用**内置数据文件**（随镜像发布、年份粒度、无网络请求、无用户数据参与），数据缺失时计算安全退化为不考虑节假日；触发日计算与节假日判定一律在服务端完成，模型只在建议理由中引用服务端提供的节假日事实。
- **轻事件边界（S09 增补）**：轻量事件是**记录**不是愿望——独立存储、应用层加密、owner 隔离；**在结构上没有提醒路径**（无触发时间字段、不在调度器扫描集合、不进入提醒发件箱），因此天然不占用每周提醒额度；轻事件不调用 Agent，不做任何统计与计数。
- **隐私**：全部内容仅用户本人可见；愿望原话、语音与照片需加密存储；不做任何形式的跨用户内容推荐或聚合分析。
- **文案约束**：产品内禁止出现「任务」「截止」「逾期」「未完成」「打卡」「连续 N 天」等词汇，统一使用「种下」「酝酿」「风来了」「正在发生」「发生过」「安静放下」。

## MODIFIED — 5.3 「不做」清单

### 5.3 「不做」清单

| 不做的事 | 原因 |
|---------|------|
| 社交、多人协作、共同愿望 | 第一版聚焦个人隐私空间，社交会改变记录时的坦诚程度 |
| 愿望的私密性分级与对外分享卡 | 全部内容默认仅自己可见即已满足 MVP；分级会引入对外可见性并稀释「私密」这一前提 |
| 自动订票、支付、下单 | 涉及资金与外部账号，超出「陪伴」的边界 |
| 天气、位置与个人日历的自动推理 | 外部数据源按路线图分步落地：**法定节假日已以内置数据文件落地（holiday-aware-timing）**；天气需要供应商选型与数据出境评估、个人日历需要 OAuth 授权与隐私边界设计，各自独立提案 |
| 模型直接发送或改写提醒 | 模型只到「提议待确认」为止；提醒是否发出、何时发出仍由确定性调度器按用户已确认的时机决定 |
| ~~轻量日常事件（「晚上吃什么」类）~~ | **已落地为 S09（lightweight-events 提案）**：独立轻量记录表 + 「先记一下」入口，结构上无提醒路径；Agent 理解与轻事件建议仍不做（见下两条的同类理由） |
| 轻事件的 Agent 理解与建议 | 轻事件保持纯记录的零摩擦；任何理解与建议都会让「先记一下」变重，属后续增强 |
| 视频记录 | 现有媒体管道仅覆盖文字、语音与照片；视频需补 MIME 白名单、大小／时长上限、分片续传与存储成本控制，另行提案 |
| 强制打卡、连续天数、完成率、排行榜 | 与「不制造焦虑」原则直接冲突 |
| 通用聊天机器人入口 | Agent 只围绕愿望对话，避免产品定位漂移 |
| 原生 App、桌面客户端、多语言 | 形态与范围收敛，见 5.1 |
