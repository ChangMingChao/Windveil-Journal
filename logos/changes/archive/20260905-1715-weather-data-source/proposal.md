# 变更提案：weather-data-source

> module: core | created: 2026-09-05

## 变更原因
来自 preferences-availability-timing 提案路线图与 holiday-aware-timing「后续提案路线」的第 2 步：天气数据源。前两个数据源提案已落地——节假日以内置文件（holiday-aware-timing）、个人日历仍排队——本提案按既定模式接入**天气**，为时机建议提供「入冬那周大概率有雨」类的事实依据。

### 隐私前置结论（本提案的成立前提）
天气必须绑定位置才有意义，而**采集位置是隐私决策**。本提案的位置来源是：**用户在 P6 主动声明的城市偏好**（`pref_key='location'`，走 S08 既有偏好的加密/撤回/删除体系）。不使用 IP 推断、不使用浏览器定位 API、不做任何静默采集——用户不声明城市，天气能力整体静默关闭。这与「节假日是公共事实、无用户数据」的 holiday 模式不同：天气是「用户主动交出的低敏感偏好 + 公共预报数据」的组合。

## 收敛决策（请重点确认）
| 决策点 | 本提案 | 理由 |
|--------|--------|------|
| 位置来源 | 用户主动声明的城市（偏好表 `pref_key='location'` 新键） | 复用 S08 偏好体系（加密、撤回、删除、可解释）；不引入 IP 定位/浏览器定位等静默采集 |
| 供应商 | **Open-Meteo 兼容**端点（免费、无鉴权、base_url 环境变量注入），抽象为 `WeatherProvider` | 与 LLM/ASR 同一供应商中立模式：代码只依赖抽象与「兼容端点」，任何同类服务可替换 |
| 使用范围 | **仅进提议上下文与建议理由**；不进 evidence 枚举 | 天气是瞬时预报（会变化），没有可持久追溯的数据条目——与 evidence「只存可追溯 ID 引用」的既有约定冲突；理由文案可引用天气事实 |
| 降级 | API 不可用/超时 5 秒/用户未声明城市 → 上下文无天气事实，一切照旧 | 与「Agent 不可用也不阻塞」同一降级哲学 |
| 请求频率 | 仅在生成时机建议（propose_timing）时按需查询，不做定时预取 | 最低成本；单用户建议频率受既有 LLM 限流约束 |

接口级

## 明确不做（本提案边界）
- 不做 IP/浏览器定位等任何静默位置采集；
- 不做逐小时精细预报（建议只需日级趋势）；
- 不做天气类提醒（「明天下雨记得带伞」超出时机场景范围）；
- 不把天气写入 evidence（瞬时数据无持久条目可指）。

## 部署影响
- 是否需要部署：是
- 部署原因：WeatherProvider 代码与新增环境变量
- 影响环境：本地 / 测试 / 预发 / 生产（生产部署仍需单独授权）
- 是否涉及数据迁移：否
- 是否需要回滚预案：是——回滚镜像即移除 Provider；未声明城市或 API 不可用时能力整体静默，双向安全
- 是否需要 smoke：不新增——外部依赖探针沿用既有「失败仅告警」约定（部署后检查第 10 项）

## 变更概述
新增 `WeatherProvider` 抽象与 Open-Meteo 兼容实现（`WEATHER_BASE_URL` 注入），在生成时机建议时：若用户在偏好中声明了所在城市（`pref_key='location'`），则查询该城市未来两周的日级天气趋势，把事实行注入提议的有界上下文——建议理由因此可以引用天气（如「入冬那周大概率有雨，适合室内开始」）。天气是瞬时公共数据：不进 evidence、不持久化、不建提醒。用户未声明城市、供应商不可用或超时 5 秒时，能力整体静默（上下文无天气事实），与产品既有降级哲学一致。位置偏好走 S08 既有体系：加密、可查看、可撤回、可删除。

## 后续提案路线（本提案不做）
1. **个人日历授权**（路线图最后一项外部数据源）。
2. **天气类轻提醒**（「明天下雨记得带伞」超出时机场景，需独立论证）。
3. **evidence 天气条目**（若需要可追溯的天气依据，需重新论证瞬时数据的引用语义）。
